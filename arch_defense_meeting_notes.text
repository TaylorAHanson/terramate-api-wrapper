Executive Summary
This working session focused on the architecture and implementation approach for integrating the EDH Self-Service Center (SSC) with Terraform/Terramate-based provisioning. The team reviewed a proposed API abstraction layer, workflow orchestration patterns, recipe/playbook-driven provisioning, dependency management, failure handling, versioning, output sharing, and implementation planning. The discussion centered on keeping SSC business-focused while encapsulating infrastructure complexity behind an orchestration layer.
Topic 1: API Abstraction Layer Between SSC and Terraform/Terramate
Discussion
Taylor presented a proposed architecture that introduces a dedicated API layer between Self-Service Center and the Terraform/Terramate platform.
Key objectives included:
Decoupling SSC from Terraform implementation details.
Removing infrastructure tribal knowledge from SSC workflows.
Providing a stable contract between business requests and infrastructure automation.
Supporting future versioning and platform changes without requiring SSC redesign.
Restricting the interface to business-oriented requests rather than infrastructure actions.
The proposed model:
SSC → API Request → Orchestration Layer → GitHub PRs → Terraform/Terramate
The API layer would:
Receive requests such as "Create Workspace."
Translate requests into provisioning actions.
Generate and manage PRs.
Coordinate multi-step workflows.
Remain intentionally lightweight.
Khiem reinforced the importance of maintaining business-focused abstractions and preventing Terraform concepts from leaking into SSC.
Key Decisions
✅ Infrastructure complexity should remain hidden from SSC consumers.
✅ API contracts should represent business capabilities rather than technical implementations.
✅ The API layer should be thin and focused on orchestration.

Topic 4: Failure Handling and Recovery Strategy
Discussion
The team examined how provisioning failures should be handled.
Discussion focused on two classes of failures:
Pre-Execution Failures
Examples:
No available subnet capacity.
Missing prerequisites.
Invalid requests.
Runtime Failures
Examples:
Infrastructure deployment failures.
Partial workflow execution.
Dependency failures.
Khiem advocated for strong pre-validation before execution begins.
Nagendra explained that Terraform state management naturally prevents resource duplication and can safely reconcile previously created resources during retries.
The team discussed avoiding rollback complexity in the MVP.
Key Decisions
✅ MVP should prioritize pre-flight validation.
✅ Automated rollback is not required for the first implementation.
✅ Terraform state should be leveraged for safe recovery scenarios.

Topic 6: Output Sharing and Persistent State
Discussion
A major technical discussion centered around sharing outputs between provisioning steps.
Example:
Workspace provisioned.
Workspace ID generated.
Future steps require the Workspace ID.
Challenges discussed:
Retrieving outputs from GitHub Actions.
Persisting results between provisioning stages.
Synchronizing execution state.
Potential approaches included:
Polling for outputs.
Persistent state storage.
Central communication tables.
Lakebase/Postgres-backed references.
Khiem suggested storing outputs centrally and passing references rather than passing values between workflow stages.
Key Decisions
✅ Provisioning workflows require persistent state.
✅ Outputs will likely need centralized storage.
✅ Additional research is required before implementation.

Overall Outcome
The team aligned on an architecture where SSC remains focused on business operations while a dedicated orchestration layer handles workflow execution, dependency management, GitHub integration, and Terraform/Terramate interaction. The major open areas remain output propagation, persistent workflow state, failure handling, and version management. The next phase is an MVP implementation supported by a dedicated sandbox environment to validate the overall approach and uncover remaining design challenges.
